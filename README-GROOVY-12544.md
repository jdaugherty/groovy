# GROOVY-12544: the InnerClasses attribute depends on what else is compiled

This branch backports [apache/groovy#3077](https://github.com/apache/groovy/pull/3077) to `GROOVY_5_1_X`.
The change is the same as on `master`, written for Java 11, which the 5.1.x line targets: `InnerClassStub` is
a final class instead of a record. This file only explains the problem and is not part of the fix.

## The problem

The [JVM specification (4.7.6)](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-4.html#jvms-4.7.6)
asks a class file to have an `InnerClasses` entry for every nested class its constant pool refers to. Groovy
writes such an entry only when the nested class is in the same compilation unit. A nested class read from the
class path, whether a pre-compiled Groovy class or a JDK class such as `AbstractMap.SimpleEntry`, gets none.

So the same source compiles to different bytes depending on what else is compiled. The implementer of a trait
is the common case: it refers to `Named$Trait$Helper`, so it has this entry only when the trait is compiled
with it:

```
InnerClasses:                                         trait in the same compilation unit only
  public static abstract Helper=class example/Named$Trait$Helper of class example/Named
```

Build tools that compare class files by content, such as build caches and the compile avoidance of
incremental builds, then see a changed class whose source did not change.

## Reproducing

- `src/test/groovy/bugs/Groovy12544.groovy` compiles a class referring to `A.B.C` and `AbstractMap.SimpleEntry`
  once together with `A` and once against a pre-compiled `A`, and compares the entries and the bytes.
- [jdaugherty/groovy-trait-incremental-compile](https://github.com/jdaugherty/groovy-trait-incremental-compile)
  shows the missing entry for a trait helper.

## The fix

When reading a class file, the decompiler keeps the class's own `InnerClasses` entries for itself and its
enclosing classes, and `AsmClassGenerator` writes them into any class that refers to it. For class nodes built
by reflection, the same entries are derived from the declaring classes. `getOuterClass()` is unchanged, so only
the generated bytecode is affected.

## Verified

- `Groovy12544` passes on this branch.
